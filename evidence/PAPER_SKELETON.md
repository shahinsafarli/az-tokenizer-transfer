# Paper skeleton

Static, hand-maintained scaffolding for paper content that the automated
pipeline does not produce. `results/paper_tables.md` is auto-regenerated by
`python -m src.analysis.report` and is overwritten in full on every run —
it holds only results-dependent quantitative tables (escape rate,
conditional macro-F1). Model description, limitations, and any other
results-independent prose belong here instead, not in that file.

## Model description

The primary (xlm15) and contrast (xlmr) base models are put through the
same tokenizer-transplant procedure against a shared donor
(`HPLT/hplt_bert_base_az`, pinned revision — see `configs/experiment.yaml`
`models.donor_revision`), which resizes and replaces the token embedding
table while leaving the encoder itself unmodified.

| Base | Tokenizer | Vocab size | Embedding parameters | Non-embedding (encoder) parameters | Total parameters |
|---|---|---:|---:|---:|---:|
| xlm15 | original | 95,000 | 97,280,000 | 151,698,434 | 248,978,434 |
| xlm15 | transplanted (donor, 32,770) | 32,770 | 33,556,480 | 151,698,434 | 185,254,914 |
| xlmr | original | 250,002 | 192,001,536 | 86,043,650 | 278,045,186 |
| xlmr | transplanted (donor, 32,770) | 32,770 | 25,167,360 | 86,043,650 | 111,211,010 |

**Methodology.** Measured directly from loaded models (`transformers
4.44.2`), not computed by hand. Original-vocabulary counts come from
architecture-only instantiation (`AutoConfig` + `AutoModelForSequenceClassification.from_config`)
— parameter count is a pure function of architecture shape, identical for
pretrained or randomly-initialized weights, so this does not require
downloading the full pretrained checkpoint to be exact. Transplanted counts
come from the real, locally-built artifacts
(`artifacts/transplanted__<base>__omp_k64_rescaled`). "Embedding
parameters" = `model.get_input_embeddings().weight.shape[0] × shape[1]`,
i.e. the word/token embedding table only — position embeddings and (for
xlm15) language embeddings are counted inside "non-embedding," matching the
formula used throughout this table. Full verification, including the
source-level confirmation in `src/transplant/build.py` that the transplant
touches only the (tied) embedding table, is recorded in `HANDOFF.md` §14.

**Required paper text** (adapt wording to house style, keep the claim
intact):

> The tokenizer transplant resizes and replaces only the input (and, where
> tied, output) embedding matrix; every encoder parameter — attention
> weights, feed-forward weights, layer norms, and, for xlm15, the position
> and language embeddings — is copied unmodified from the pretrained base
> checkpoint. Consequently the 25.6% (xlm15) and 60.0% (xlmr) drops in
> total parameter count after transplant are embedding-table size only,
> driven entirely by the donor vocabulary (32,770 tokens) being smaller
> than either base's original vocabulary (95,000 for xlm15; 250,002 for
> xlmr). This is the treatment — a change in tokenization and vocabulary —
> not a capacity confound: the non-embedding (encoder) parameter count, the
> part of the model that does the actual sequence modeling, is unchanged by
> the transplant for both bases.

## Limitations

### Base models are not capacity-matched (recorded 2026-09-04, before results)

xlm15 has 151.7M non-embedding parameters; xlmr has 86.0M — a factor of
**1.8×**. The two bases were selected for their pretraining-data properties
(Azerbaijani absent from xlm15's pretraining vs. present in xlmr's — see
`configs/experiment.yaml`'s `models.primary`/`models.contrast` notes and
`HANDOFF.md` §3.4), not for matched capacity. Consequently, **any cross-base
difference observed in the results (e.g. in escape rate or conditional
macro-F1) cannot be attributed to pretraining-language-coverage alone** —
model capacity is a plausible alternative or contributing explanation and is
confounded with the base-model assignment by construction. Recorded now,
before any post-freeze result exists, specifically so it cannot be added or
omitted depending on which direction the results run.

### Other limitations flagged during the project, not yet consolidated here

Flagged as "belongs in Limitations" at the point each was discovered, in
`HANDOFF.md`'s running log; still need their full write-up pulled into this
document before submission — listed here so none get lost:

- **Condition 3 confound**: tokenizer replacement bundles segmentation and
  orthography changes together (`HANDOFF.md` §3.6, "Decision (confirmed):
  Option C").
- **Noise×condition interaction**: no association found (Fisher p=1.0000,
  OR=0.625, n=66) — to be reported as a null result at limited statistical
  power, not as ruling out a large true effect (`HANDOFF.md` §3.12, around
  the `noise_interaction.json` discussion).
- **Label noise level**, if the T6 audit landed in the 85–90% band rather
  than ≥90% (`HANDOFF.md`, label-audit gate table).
- **Noise-attenuation figures** for symmetric label noise, computed
  regardless of outcome (`HANDOFF.md`, "Noise-attenuation figures — record
  now, they belong in Limitations regardless of outcome").
